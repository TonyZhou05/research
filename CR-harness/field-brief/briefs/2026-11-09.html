1 · Stale instruction files: task success hides documentation-debt interest

watch arXiv:2611.09802. Repository instruction files such as AGENTS.md and CLAUDE.md are read in every coding-agent session. When they fall behind the code they become documentation debt, and the interest is the cost added to every later run. Evaluations that check only task success can miss that cost, so the stale file persists. The authors study three real-world stale instructions from active open-source repositories, each a different kind of guidance: a test command, a code location, and a procedure for adding a component. Agents completed 22 maintenance tasks under three versions of each instruction (left stale, corrected to the current path, and removed), with the code and the task held fixed, and the authors analyze 732 trajectories of two models at the level of individual tool calls. Agents followed stale guidance when it was relevant to their tasks, sometimes even when correct information was available elsewhere. On the stale test command, Claude Sonnet 5.5 needed about two extra tool calls per run — a third more than with the corrected command; in the other two cases, no difference was detected. Agents generally recovered from the immediate failures, but none repaired the underlying instruction file. Correcting the instructions eliminated operations on obsolete paths; removing them prevented most.

For CR: a win/loss or “task passed” grade will hide the same tax. ETL should count extra tool calls and obsolete-path operations, not just match outcome. A stale cockpit note or outdated legal_actions comment is a harness defect the agent is unlikely to fix on its own — pairs with harness-is-the-model-action-log (grade the action log) and arcbench-rules-under-compaction (keeping a rule in context is not the same as following it).

2 · Knowing when to intervene: treat the audit as a causal question

watch arXiv:2611.09792. Static agent benchmarks do not say whether an intervention partway through a trajectory — verifying the current output or steering the agent, by a human, a costlier model, or slower supervision — would improve the final outcome. The authors treat that as a causal-inference problem: the effect of intervening depends on the current context and on the agent’s future behavior. They present a framework for evaluating the causal effects of randomized interventions inside agent trajectories. From a relatively small dataset of trajectories collected under randomized interventions such as verification or screening, they estimate the dynamic causal effect of a rich class of contextual intervention policies. The same structural parameters can build safety leaderboards that rank the risk of various agentic actions for audit prioritization. Applied to τ-bench Retail, ToolSandbox, and ImpossibleBench, intervention effects varied substantially across agent actions and states. The abstract does not report a single headline percentage; the claim is methodological.

For CR: this is the eval question behind the escalate-vs-act gate at decision_point. Does intervening (Jev fallback, dual-LGTM, a human review) improve the match from this state, and which actions are worth the audit budget? Grade intervention policies on their causal effect, not only overall win rate. Pairs with stepgate-step-level-escalation, reflex-jev-selective-control, and the Jev router shortlist.

Pointers (not carded)

  • When Routine Operations Break Architectural Pattern Relationships (PatternOps): across five released harnesses, a routine operation (reapplying a plugin or saving an allow rule) silently broke a Guardrail Enforcement Point relationship — policy stopped evaluating edits while every plugin stayed active, and a prohibited edit executed. Pattern relationships are properties of the running system and its history, not of the source tree. Left as a pointer so the oversized board does not grow a third card today; relevant to how CR should regression-test legal_actions after config changes.
  • BOXBOX: agent-triggered harness revision with kernel-managed hot reload during a long-running software-performance task (PerfRace). Reports Speedup@4h of 1.70× vs 1.54× for the strongest baseline (Frozen Harness / offline Harness Evolution / Harness Scaling). Overlaps the already-watched exo-runtime-harness-self-revision and kpharness-knowledge-probing-revisions cards.
