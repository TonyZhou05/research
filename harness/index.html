1. Thesis

The harness is not “one mega-agent.” It is a small company of specialists with clear ownership, shared memory (when the vault exists), and a few locked pipelines. Chat is a digest; proof of done is an artifact path and/or a live URL.

  • Specialize — Manage Bot owns roster/onboarding/Lab; Mac CLIs are the workers; a future Github Bot owns the coding EM loop.
  • Share context — every agent reads/writes the same Obsidian vault before and after work. vault scaffolded
  • Balance capacity — when Field Brief collect stands, rotate Muse / DSH (and Agy if installed) so no single quota carries the load.
  • Survive reconnects — long Mac jobs go through tmux + streaming heartbeats + a stale-log watchdog. helpers installed
  • Human gates stay human — merges, payments, sends, deletes, and production require Tongli only.
  • Decide cheap, execute expensive — Jev (typed route) is the target front-door before fan-out. target

5. EM task loop (intent → plan → PR)

This is the fleet coding contract to grow into — same semantics as the reference EM loop. A Github Bot EM room is the intended babysitter; it is not wired yet. Until then, Manage Bot + Tongli hold the gates manually.

CR-Harness note: private repo TeachFakerPlayingMid/CR-Harness-main uses its own issue-first Claude CONTRIBUTING flow (see /CR-harness/). That stays. This playbook’s intent→spec→plan→PR is the fleet contract for other work and for growing the EM room — not a rewrite of CR’s local norms.

Roles

RoleWhoJob
Product ownerTongliAccepts intent.md / spec.md; only merge & production gate
EMGithub Bot not yet (Manage holds interim)Commits artifacts, fires the next play, triages review, starts the next independent slice; heartbeat babysitter
ImplementerClaude / Fable (default) or Muse/DSHImplements from accepted plan.md; opens PR; cannot be a dual-LGTM reviewer on the same PR
ReviewersAstra (Codex) + Fable (Claude)Blind dual LGTM on the PR (each sees PR + intent/spec/plan only — never each other’s reviews); dual LGTM = agent-complete, not shipped
Research originatorhuman or scout botWrites Stage‑1 intent.md — not a coding task

Artifact chain

intent.md → spec.md → plan.md → PR + tests → dual review → human merge → pipeline ↑ │ └──────── incident / broken demo / failed control band ──────────────┘
  • An accepted intent.md triggers design.
  • An accepted spec.md triggers plan mode.
  • An accepted plan.md triggers Claude implementation.
  • A PR URL existing triggers Astra + Fable blind dual-LGTM (never before; implementer ≠ reviewer).
  • Dual LGTM + product-owner merge triggers ship. Dual LGTM alone is not merged.

What each markdown is for

intent.md Problem, why now, constraints, non-goals, success signal. Written by research/product — not by the implementer inventing scope mid-build.
spec.md Observable behavior / acceptance criteria the reviewers will check against. Product owner accepts before plan mode.
plan.md Ordered slices, claim map, files to touch, test plan, and “done” definition. Implementer works from this file; reviewers check the PR against it. Review fix passes append a short record instead of rewriting history silently.

Play-by-play (one slice)

  1. Read context — EM + implementer pull standing rules, Decisions, prior Ship notes (vault when it exists).
  2. Commit intent → spec → plan if missing (any slice bigger than a one-line fix).
  3. Tongli accepts intent/spec when the change is consequential.
  4. EM launches implementer via durable Mac launch (tmux + stream + watchdog when stood up); prompt points at the committed plan.md.
  5. Implementer builds, runs the repo’s one-command tests, commits, pushes, opens the PR — does not wait for reviewers.
  6. EM requests Astra + Fable on the PR URL independently (blind dual-LGTM).
  7. EM triages — P0/P1 block dual LGTM; P2s get a fix pass on the same branch/session id.
  8. Dual LGTM → ping product owner. Merge only if Tongli asked (or a standing order for that repo).
  9. File proof — note with PR URL, session ids, follow-ups.
  10. Next independent slice starts without waiting on org APPROVE of the previous one.

What the EM does not do

  • Start Codex/Kimi review before there is a PR URL.
  • Treat dual LGTM as merged.
  • Stall the next independent slice on org APPROVE.
  • Cold-start Claude/Codex/Kimi when a session id for that PR/slice already exists.
  • Put Tongli back on the critical path of mid-build approval prompts.
  • Forward one reviewer’s findings into the other reviewer’s kickoff (breaks blind dual LGTM).

14. Three-Run Proof · kill review · GYR

Three-Run Proof

Before enabling a new routine: Observe (bot charter/handoff/skill, not the artifact by hand) → Correct on a second input → Release after a third consecutive clean run (or three checkable proofs). Do not automate the first successful run.

Weekly kill review

Paired with Monday playbook↔card sync. For each Manage routine: did it run? was the output right? would we miss it if killed? Pause or delete zombies. Spot-check one output by hand.

GREEN / YELLOW / RED (reversibility)

TierRuleExamples
GREENDo it; log itsearch, read, summarize, draft, vault note, research
YELLOWAllowed inside approved tools / laneshub edits under lane, saved routines, Mac CLI on named repos
REDAlways ask Tonglisend/publish, spend/pay, merge, delete non-junk, permissions, production, accept terms

Uncertainty: if you cannot undo it in under a minute, park and ask.

Closed proof loop

Checkable proof before “done”: green CI / exit code, live URL, or before/after screenshot. Summaries are intent. Fail-closed: prose “done” cannot pass without a mechanical artifact or an independent read-only check.

Run limits + autonomy

  • Long fires inherit defaults: limited items · ≤2 retries · $0 spend · 0 external actions without Tongli approval.
  • Abnormal volume vs last clean run → stop and escalate.
  • Autonomy ladder 0–4 with demotion when quality drops.
  • Park unknown outcomes after crash/dirty exit — do not auto-retry guessing.

15. How to extend the team

Architecture tips that survive a day get filed in Harness Lab; if a KEEP changes how we run, patch this playbook the same day.

  1. Decide the layer — Grok bot (orchestrator) vs Mac CLI (worker).
  2. Agent Manage Bot creates/organizes Grok bots; onboards Mac CLIs (binary, auth, usage card).
  3. Vault — when stood up: add agent card, update Roster + AGENTS.md, file a Decisions lock.
  4. Hooks — extend installer if the CLI has an AGENTS/skills home.
  5. Routines — owning Grok bot schedules the cron/event listeners; Three-Run Proof before Active.
  6. Usage — add a collector + card in playground usage-dashboard, refresh, push.
  7. Never put keys in the vault or hub HTML. Rotate anything pasted into chat.
