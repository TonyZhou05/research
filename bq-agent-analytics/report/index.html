TL;DR

  • Read-only consumer over one table. Producers write agent_events; the SDK reconstructs traces, evaluates, classifies, and builds a context graph with BigQuery SQL and BigQuery AI functions (README).
  • User-intent analysis already exists, but it is shallow. deep_analysis() classifies questions one at a time into a fixed or user-supplied label list. insights() tags sessions against hard-coded goal, outcome, and friction vocabularies. Nothing discovers intents, and nothing persists them.
  • Momentum is on evaluation and self-improvement. The roadmap calls the self-improvement loop “the next center of gravity” (#96). Recent releases add EvalBench, G1 taxonomy, unified evaluators, and ADK 2.0 views.
  • Best entry for me: dogfood the Claude Code plugin on my own fleet, then contribute intent discovery and a persisted, configurable intent taxonomy. That is the gap between what the SDK already has and what intent analysis needs.

What it is

The package bigquery-agent-analytics (Apache-2.0, “Development Status :: 3 - Alpha”, Python 3.10–3.14) describes itself as a “consumption-layer toolkit for agent observability, analysis, evaluation, and advanced capabilities like the Agent Context Graph” (README, pyproject.toml).

Producers write, the SDK reads. The ADK BigQueryAgentAnalyticsPlugin and the LangChain/LangGraph BigQueryCallbackHandler “emit the same schema and can write to the same table side by side”. The SDK is “read-only over that table” (README §How this fits together). The repo now also hosts its own producers: bigquery-agent-analytics-tracing (a writer/drainer, an OTLP receiver, and a Claude Code plugin with nine hooks) (producers/README.md).

from bigquery_agent_analytics import Client, TraceFilter
client = Client(project_id="my-project", dataset_id="analytics",
                table_id="agent_events", location="US")
traces = client.list_traces(TraceFilter(limit=1))
traces[0].render()

Data model: agent_events

One time-partitioned table with one row per event. The columns below are the ones the SDK’s own seeder creates (seed_events.py#L53):

ColumnTypeRole
timestamp · event_typeTIMESTAMP · STRING (required)Partition key; event taxonomy below
agent · session_id · invocation_id · user_idSTRINGIdentity. session_id is reusable, not unique; ambiguous reads raise AmbiguousSessionError (README)
trace_id · span_id · parent_span_idSTRINGSpan tree / DAG reconstruction
status · error_messageSTRINGErrors via ERROR_SQL_PREDICATE
content · attributes · latency_msJSONPayload (e.g. $.text_summary on user messages), ADK metadata, timings
is_truncatedBOOLEANContent was truncated by the producer

Event families (event_semantics.py#L138): user (USER_MESSAGE_RECEIVED), invocation, agent (incl. AGENT_TRANSFER, AGENT_STATE_CHECKPOINT), llm (LLM_REQUEST/RESPONSE/ERROR), tool (TOOL_STARTING/COMPLETED/ERROR/PAUSED), state (STATE_DELTA), six HITL events, and ADK 2.0 compaction and workflow-node boundaries. ViewManager unnests each type into a typed view (for example adk_llm_requests) and deploys cross-event views such as compaction_windows (SDK.md §15).

What matters for intent analysis: the user’s words live in USER_MESSAGE_RECEIVED.content (text_summary). The outcome signal is spread across tool errors, HITL events, the final response, and optional categorical_results.

Intent analysis today

Four surfaces already answer “what are users trying to do?”:

SurfaceHow it worksRef
client.deep_analysis(AnalysisConfig(mode=…))Modes: frequently_asked (GROUP BY exact text_summary), frequently_unanswered (questions in sessions that had any error), auto_group_using_semantics and custom (one AI.GENERATE call per question: “Classify this question into exactly one category”, temperature 0, output category STRING). Falls back to legacy ML.GENERATE_TEXT, then to frequently_asked; details["grouping_mode"] records which path ran.feedback.py#L244 · #L840
client.insights(InsightsConfig)An LLM writes per-session facets (goal_categories, outcome, satisfaction, friction_types, session_type, key_topics, …) against fixed vocabularies, then aggregates them (goal_distribution, outcome_distribution) and writes the seven report sections.insights.py#L62

client.drift_detection() · UserProfileBuilderCoverage of golden questions in production traffic; per-user “common requests” and topics.SDK.md §9, §11

Gaps and limitations

  1. No intent discovery. “Auto group using semantics” with no categories falls back to six hard-coded generic labels (feedback.py#L875). No embedding clustering or taxonomy induction exists. AI.EMBED is only used for drift.
  2. Closed vocabularies in insights. GOAL_CATEGORIES, OUTCOMES, FRICTION_TYPES, and SESSION_TYPES are module constants, and labels outside them are dropped (insights.py#L815). Domain intents such as “refund status” cannot be expressed there.
  3. Intent is not persisted. Insights facets and question distributions come back as in-memory Pydantic objects, so there is no intent time series. Only the categorical evaluator persists.
  4. Question-level, not session-level. Grouping classifies each USER_MESSAGE_RECEIVED row on its own. Multi-turn goals, intent shifts, and corrections are not modeled in core (#429).
  5. Exact-match heuristics. frequently_asked and keyword_overlap drift use whole-string equality after lower/strip (feedback.py#L520). frequently_unanswered counts a question as unanswered if any event in its session errored (feedback.py#L285).
  6. Small default samples. TraceFilter.limit defaults to 100 and InsightsConfig.max_sessions to 50 (trace.py#L577, insights.py#L251). Fine for exploration, but corpus-level intent work needs explicit, cost-aware batching.
  7. Truncated input. Intent SQL reads content.text_summary. The schema carries is_truncated, but the grouping queries do not use it.
  8. Producer/schema governance. No column-level projection (#321); custom_metadata capture limited to a2a:* keys (#320). Both matter if intents need PII-safe inputs or custom labels.
  9. Alpha surface, heavy API. The classifier says “3 - Alpha”, and #128 asks to simplify the API and add API docs.

Ranked candidate intents

Ranked by leverage for intent analysis × fit with where upstream is heading × how quickly I can land it. Nothing here has been filed upstream.

Size M

Dogfood BQAA on my own agent fleet (Claude Code + Codex → BigQuery), then run intent analysis on it

Why. Gives real, owned traces instead of seeded demo data. The repo ships a Claude Code tracing plugin (nine hooks) and an OTLP receiver path for Claude/Codex telemetry. Upstream explicitly lists the Claude Code plugin as a contributor-onboarding target.

What. Point the plugin at a personal dataset, run ViewManager.create_all_views(), then insights() / deep_analysis() / evaluate_categorical() over my own sessions. Write up friction found during setup as candidate upstream fixes. Needs a non-production GCP project.

Evidence: plugins/claude_code · producers/ · deploy/otlp_receiver · #475 (onboarding: Grafana + Claude Code plugin) · #372 · #317 (Codex OTLP design, blocked on #316)

Size M

Real intent discovery: replace the fixed six-label “auto group” with embed → cluster → name

Why. AnalysisConfig(mode="auto_group_using_semantics") reads like clustering, but with no custom categories it classifies each question into a hard-coded list (General Inquiry, Technical Support, Account Management, Feature Request, Bug Report, Other). So it cannot surface intents nobody thought of.

What. New mode (e.g. discover): AI.EMBED the USER_MESSAGE_RECEIVED text, cluster in BigQuery ML (k-means), have an LLM name each cluster from sampled members, and return an induced taxonomy that can be fed back as custom_categories. Reuses the existing AI.EMBED plumbing from semantic drift.

Evidence: feedback.py#L875 (default labels) · feedback.py#L320 (per-question AI.GENERATE classify) · feedback.py#L114 (AI.EMBED already used for drift) · #74 (insights-from-traces papers)

Size S–M

Configurable, persisted intent taxonomy in insights()

Why. Session facets use module-level vocabularies (14 GOAL_CATEGORIES, 5 outcomes, 12 friction types, 5 session types). Labels outside the list are silently dropped (goals fall back to other). Facets are returned in memory, not written to a table, so there is no intent history to trend.

What. Add taxonomy overrides to InsightsConfig and an opt-in persist_results that writes facets to an append-only table with a latest-per-session view, following the pattern categorical_results already uses (schema, then writer, then views).

Evidence: insights.py#L62 (GOAL_CATEGORIES) · insights.py#L815 (out-of-list labels dropped) · insights.py#L251 (max_sessions default 50) · #63 (Quality Scorecard reuses categorical persistence)

Size M

Intent × outcome views: which intents fail, stall, or cost the most

Why. The analysis that matters for an intent is how it connects to outcomes. Today frequently_unanswered groups on exact question strings and counts any session with any error event. There is no view joining intent to outcome, friction, tool errors, latency, or cost.

What. Session-level intent (first message or LLM-summarized goal) joined to the per-event views and categorical_results, giving intent_outcome_matrix / intent_cost cross-event views registered in _CROSS_EVENT_VIEW_DEFS, plus a Streamlit/Grafana panel.

Evidence: feedback.py#L285 (frequently_unanswered SQL) · views.py (cross-event registry, landed in #489) · dashboards/ (Streamlit #480; Grafana moved there in #481)

Size S–M

Intent-level drift and coverage (golden vs production intents)

Why. drift_detection() defaults to keyword_overlap, which is really case-insensitive exact matching of whole questions. The embedding path only runs when an embedding model is passed, and it compares questions, not intents.

What. Make the semantic path easy to reach from the CLI, and add a coverage report per intent cluster (golden share vs production share, uncovered clusters with examples). That report can feed eval-set curation directly.

Evidence: feedback.py#L520 (keyword_overlap) · feedback.py#L540 (cosine threshold 0.3) · #318 (quality flywheel) · #436

Size M–L

Multi-turn intent shift and correction tagging in core

Why. Intent is not static within a session. Upstream already wants the parroted/recovered correction tagger moved out of scripts/quality_report.py into a library surface. Per-turn intent tags are a natural sibling.

What. Contribute to or build on #429: a core turn-segmentation module that emits per-turn tags (intent, correction, recovery) in the sub-trajectory shape the judge reports and skill-evolution already expect.

Evidence: #429 · scripts/quality_report.py

Size L

Intent-stratified synthetic eval sets from real traces

Why. RFC #436 proposes deriving eval cases from production traces. Stratifying by discovered intent keeps rare intents from being drowned out by head traffic.

What. After intents 2 and 3 exist: sample per intent cluster, generate tasks, expected trajectories, and near-misses, then emit an EvalSuite tagged by intent.

Evidence: #436 · #95 (automated benchmarking) · SDK.md §7 Eval Suite Management

Size L

Tie intents to the AgentForensics failure taxonomy

Why. RFC #435 (27 comments) proposes an automated failure taxonomy with span-level auditing over BQAA traces. An intent × failure-category matrix is the missing join between “what users wanted” and “where the agent broke”.

What. Watch or join the RFC. Offer the intent dimension as a grouping key for its reports once G1 labels are persisted (EvalBench span-level G1 labels landed in #470).

Evidence: #435 · docs/week0_g1_taxonomy.md · docs/evalbench.md

Size L

Side-by-side behavioral diff per intent

Why. Wish-list item #1 is SxS diffing of two agent runs to find the divergence point. Scoping it per intent keeps the comparisons interpretable.

What. Given two releases or experiments, align sessions by intent cluster and report the divergence step, using the existing deterministic replay/compare utilities (SDK.md §4).

Evidence: #10 · SDK.md §4 Deterministic Replay

Size S

Document the intent-analysis surfaces (API docs)

Why. The intent-relevant APIs (deep_analysis, insights, drift_detection, evaluate_categorical) are spread across SDK.md §9, §10, and §16, and the fixed-label behaviour is not called out. #128 asks for API docs.

What. A single “User-intent analysis” guide with defaults, limits, and cost notes. Low-risk as a first PR, and it builds the familiarity the bigger intents need.

Evidence: #128 · SDK.md
