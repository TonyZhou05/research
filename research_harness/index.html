Auto-Research Harness

A working note on how to build a harness for automated research: the stage × layer framework, the four-layer architecture (pipeline, tree search, decision layer, world model), the minimal closed loop, and how we intend to evaluate it. Distilled from a Chinese-language survey post, with a small offline reference implementation on the box to test the mechanics.

1. Overview

Automated research is no longer one prompt. The post’s through-line: judgment, selection and evaluability — not generation — are the bottlenecks. A good harness therefore spends its design effort on four things: a frozen way to score results, a search structure that turns failures into information, a cheap preference layer that decides what is worth executing, and human gates at the few irreversible points.

Minimal closed loopOne human-written goal, one frozen evaluator, one editable file. Modify → run a fixed short budget → evaluate → keep if better, reset if not.
Four cross-stage insightsStructure moves linear → loop → recursive; compute budget is a first-class variable; human-in-the-loop is an interface-design problem; benchmarks move toward “distance from human”.

3. Four-layer harness architecture

The post’s synthesis: an auto-research harness has four layers. Each answers a different failure mode.

5. The harness loop

The minimal closed loop in the post is karpathy/autoresearch (an open-source project, no paper): three files. prepare.py is the frozen evaluation and the trust boundary; train.py is the only file the agent edits; program.md is the human-written goal. The agent modifies code, runs for about five minutes, evaluates, commits if the metric improved, otherwise resets. On one H100 that is roughly 100 experiments per night; the post cites a reduction of “Time-to-GPT-2” from 2.02 h to 1.80 h.

The post’s observation about structure: 2023 linear pipeline (a failed stage ends the run) → 2024–25 loop (failure becomes information; the system can go back upstream) → 2026 recursive (cross-round learning: earlier experience shapes later search). The lessons pool is our recursion hook.

6. Operators & tree search

AI Scientist-v2: agentic tree search in four stages

AI Scientist-v2 (Yamada et al., 2025) organises experiments as a tree. Stages: preliminary investigation → hyperparameter tuning → research-agenda execution → ablation, with the best node of each stage seeding the next. Node types: non-buggy, buggy, hyperparameter, ablation, replication, aggregation, and “best”. Non-buggy nodes go to a refine branch, buggy nodes to a debug branch.

Reported outcome (per the post): 3 papers submitted to an ICLR 2025 workshop; one accepted (average 6.33). A self-check then found roughly 57% train/test overlap (data leakage), and none of the three met main-conference standards. This is the reason our leakage gate is mandatory.

AIRA: the decision-layer view

AIRA (Toledo et al., 2025) formalises a research agent as (search policy, operator set, fitness function). Each round: select a node, select an operator (draft / debug / improve), score the result. The counter-intuitive finding: the bottleneck is the operator set, not the search strategy — with AIDE’s operators restricted, better search strategies produced no gain.

Medal rate, as read from the post’s chartValue

Our harness: the operator set is a per-task plug-in (draft, debug, improve, hyperparameter, ablate; replicate and aggregate are pipeline steps). Search policy is simple on purpose — priority = normalised fitness − a cost penalty + an exploration bonus (the MARS-style efficiency-guided idea) — so improvement effort goes into operators.

7. RPM-style candidate selection

RPM (Foster et al., 2026) inserts a preference layer before the executor. Per round: (1) select a parent node; (2) generate N unexecuted child candidates in parallel; (3) pick one of N by a head-to-head pairwise tournament that sees the context of previously executed solutions; (4) execute only the champion.

Problem downgrading. Instead of asking a model to predict an absolute score (which needs calibration), ask which of two candidates is better (which needs only consistency) — easier for frozen pre-trained models.

VariantMechanismTrade-off (post)
Inference-onlyLLM-as-judge over plan, code and historyFast, no extra GPU; prompts tuned with DSPy MIPROv2
AgenticRun a small pilot experiment in a sandbox before decidingSlower, more accurate

Reported curve: inference-only RPM starts higher; agentic RPM starts slowly, then overtakes (around hour 15 on the post’s chart); both finish above the no-RPM baseline.

Time-inflation trick. The post says the real pilot budget was 300 s while the prompt claimed 2700 s (9×), because a model told time is very tight becomes unwilling to explore. We treat this as an optional, off-by-default prompt nudge: the real cap is still enforced and the ledger records whether the note was used.

Our harness: a round-robin tournament where every pair is played in both orders (cancels position bias), with pluggable judges: a heuristic stub for the demo, a random control, an inference-only LLM-judge interface, and an agentic pilot judge that scores a small train-only validation slice.

8. Budget as a first-class variable

  • The post sees compute budget treated as a decision variable: RPM (budget as preference ranking), MARS (budget-aware MCTS with efficiency terms), and Karpathy’s fixed 5-minute budget that constrains the search space.
  • Counter-evidence from RE-Bench (Wijk et al., 2024) as cited: at 2 h the AI scores about 4× the human median; humans overtake at 8 h and are about 2× better at 32 h — humans get higher marginal returns from extra time.
  • Our harness: wall-clock and cost caps per run and per node; evaluator timeouts derived from them; exhausting a run cap ends the run gracefully with no report. Comparisons between methods must be budget-matched.

9. Leakage gate & frozen evaluation

  • Frozen evaluator. Data, split and metric live in one file whose checksum is pinned by a human. The harness verifies it before and after every run and refuses any change outside the one editable file.
  • Leakage gate (mandatory). After each evaluation, training keys are compared with evaluation keys reported by the frozen evaluator; any overlap, or a candidate that references the evaluator, marks the node leaky. A leaky node can never become “best”, and the report builder refuses to run without a passing gate on the best node and on every replicate.
  • Append-only ledger. Every node, tournament, evaluation, gate decision, commit/reset and lesson is a hash-chained JSONL record (tamper-evident, not tamper-proof).

10. Human gates

The post frames human-in-the-loop as an interface design problem: not whether, but where. Intervene at high-leverage points and do not ask at every step.

GateTriggers
direction_changeA proposal that moves the search into a new family of solutions
public_interface_changeThe candidate’s exposed interface differs from the starting one
irreversible_or_high_riskCode touching processes, network, deletion, writes or dynamic execution
final_reportBefore any report counts as final; otherwise it stays a draft

Policy is a small config per task; each request and decision (who, why) is written to the ledger. Unattended demo runs use a scripted approver and say so in the ledger. This matches the fleet rule that merges, payments, sends and production stay with Tongli (GREEN / YELLOW / RED).

11. World model & synthesis caution

Kosmos (Mitchener et al., 2025) pairs a data-analysis agent and a literature-search agent that share a structured world model. Per the post, one run involves about 200 rollouts, about 42,000 lines of code and about 1,500 papers.

Accuracy (as reported in the post)Value
Data analysis~85.5%
Literature review~82.1%
Interpretation / synthesis~57.9% — the bottleneck
Overall~79%

Caution for us: reading and coding are the strong parts; combining data results with literature is the weak one. Treat any synthesis claim from an agent as a hypothesis for a human, never as a finding. Our harness only has a thin stand-in for this layer (lessons pool plus ledger); a real structured world model is future work.

12. Benchmarks & our evaluation plan

The post’s fourth insight: benchmarks move from completion toward distance from human — and ultimately toward whether science can be rediscovered.

How we evaluate our own harness

  1. Frozen evaluation. One human-reviewed evaluator per task, checksum-pinned; the candidate never sees held-out data.
  2. Hold-out and replication. Report the best node and the starting candidate on the same extra data seeds (mean and spread), never a single lucky run.
  3. Leakage first. A result with no passing leakage gate is not a result.
  4. Ablations. Every claimed gain comes with component ablations (informational nodes that cannot be promoted).
  5. Budget-matched comparisons. Compare selection strategies (no preference layer vs. tournament judges) at equal executed-node and wall-clock budgets; remember the RE-Bench lesson that rankings can flip as the time budget grows.
  6. RCBench-style rediscovery (planned). Pick a known, published result with a computable ground truth, withhold the answer, and score whether the loop reproduces it (our own rubric: reproduce = parity, beat = candidate new finding needing human review). Not yet run.
  7. Distance from human. Where possible, record a human baseline for the same task and budget and report the gap, not just a pass/fail.

13. How to run

The reference harness is a dependency-light Python package (standard library only) that lives on the box and is not published here yet. In outline:

  1. Write the task: a human-written goal file, a frozen evaluator, and a starting candidate file; pin the evaluator’s checksum.
  2. Choose operators and a judge: stub operators and a heuristic judge for the offline demo; later, model-backed operators and an LLM or pilot judge supplied as plain callables (no keys are needed or stored by the harness).
  3. Set budgets and gate policy: run and node caps for time and cost; which gates need a human.
  4. Run: the runner executes baseline → preliminary → tuning → execution → ablation/replication, commits improvements in a throw-away git sandbox, and writes the ledger, lessons and a draft report.
  5. Review: verify the ledger chain, read the report and gate log, approve or reject. Nothing is published without Tongli.

Model-written code must run in a container or VM for real use: the evaluator subprocess only has a timeout and a clean environment, not security isolation.

14. Reference implementation status

Everything below ran offline on the box with deterministic stub operators on a toy regression task; it shows that the mechanics work and says nothing about LLM-driven research quality.

  • Components built: frozen-eval checksum boundary, search tree with node states, draft / debug / improve / hyperparameter / ablate operators, staged pipeline with best-node handoff, replication and aggregation, pairwise-tournament selection with four judge types, budget tracker, leakage gate, human gates, git commit/reset sandbox, hash-chained ledger, lessons pool.
  • Tests: 25 pytest tests pass (ledger tamper detection, frozen-boundary violation, commit/reset, leaky candidate blocked, only the champion executed, gate denials, budget exhaustion, determinism, full run).
  • Demo run (seed 0): held-out error falls from about 0.78 to about 0.011 (the toy’s noise floor is about 0.01) over roughly 38 executed nodes in about 2 s, with a buggy draft repaired by the debug operator and one direction-change gate approved.
  • Selection comparison (5 seeds, equal node budget): the three tournament variants reached similar best error (≈ 0.0112); the no-preference control was close at the median but had a clearly worse mean because some seeds got stuck. The toy is too easy to separate the judges — treat this as a smoke test, not evidence for or against RPM.

16. Honest caveats

  • This page is a summary of a secondary source (a Chinese-language survey post). Numbers, dates and attributions may contain errors from the post or from our reading of its screenshots.
  • Chart values (AIRA medal rates, RPM curve) were read from figures in the post; treat them as approximate where they are not in prose.
  • The reference harness is a toy. A passing demo does not show that an LLM-driven loop will do good science.
  • The gates reduce risk but do not replace running untrusted code in a real sandbox.
